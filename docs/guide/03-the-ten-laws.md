---
title: The ten laws
classification: Public
---

catalyst asks an agent to judge ten things for itself. Everything else, the CLI, the journal and `catalyst check`
enforce. The laws are short on purpose: an agent loads only them at the start of a session, and `catalyst why <law>`
explains any one in full. A module may add up to three laws of its own; the software-engineering module adds one
(below).

Each law comes from numbered invariants (`INV-n`), which are the checks behind it. A law says what to do; an invariant
says what is verified.

## L1. Record every change, as it happens

Every change to a governed file is journaled when it is made: who, why, which rules, and each file's content before
and after. A record is never reconstructed afterwards. Work done outside catalyst, straight into git, is adopted into
the journal or reverted.

- **Kept**: the agent edits `reset.py`, then runs `catalyst journal append` naming the bug and the rule, before moving
  on.
- **Broken**: ten files changed in a session, and one journal entry at the end "for everything". `catalyst check`
  reports each file whose state no entry records.

## L2. Ground every change

Work traces to an artifact, the artifact to a rule, the rule to a domain. A commit names its artifact or rule, or is a
`chore:` that changes no rule's behaviour. The agent states the tier first (chore, fix, feature) and escalates it if
the work grows.

- **Kept**: "This is a fix: it restores `br-AUTH-000003`. Opening a bug against it."
- **Broken**: a "small cleanup" that changes what the reset link does, committed as `chore:`.

## L3. Assent before push

Nothing leaves the machine without the user's explicit yes: no push, no share, no pull request, no publication. No
commit lands in a project without it either. A catalyst command that exits `3` is asking: the agent shows what it
printed and re-runs it with `--yes` only once the user agrees.

- **Kept**: `catalyst share push` prints the files it would publish; the agent shows them and waits.
- **Broken**: re-running with `--yes` straight away because the change "looked safe".

## L4. Humans decide, agents do the work

A conflict, a disputed version or a rejected finding becomes a reconciliation case (`RECON-`) for a person. The agent
never resolves a merge, never approves its own work, and never signs for someone else. Who signs is verified, never
guessed.

- **Kept**: two teammates changed the same requirement; the agent opens a `RECON-` case with both versions.
- **Broken**: the agent picks the version it prefers and writes it.

## L5. The criterion lives outside the project

A project holds `catalyst.toml` and nothing else of catalyst. Every agent, tool and machine finds the criterion with
`catalyst where` and readies it with `catalyst open`.

- **Kept**: a new machine clones the project and runs `catalyst open`.
- **Broken**: copying the criterion into the project's tree "to make it easier to find".

## L6. Never hand-edit what is generated or frozen

Indexes, backlogs, composed documents and back-references are regenerated by their commands. A deployed definition, or
a superseded template, changes only by migration.

- **Kept**: a requirement's `Steps` field fills itself when a step names it as its parent.
- **Broken**: editing `requirements.md`, the index, by hand to fix a title.

## L7. IDs are permanent

An ID is unique, signed with its creator's userid, and never reused or renamed. A retired thing is retired in place,
never deleted. The signers ledger is never rewritten.

- **Kept**: a rule that no longer applies is marked retired, with why and what replaces it; its ID still resolves.
- **Broken**: deleting it, or giving its number to a new rule. Even mentioning an ID before the CLI allocates it is a
  mistake: the CLI counts every ID the journal names as used, so that number is never handed out.

## L8. Install, sync and share only when asked

Each happens only on the user's request, with its own command. Reading catalyst never installs it.

- **Kept**: "Shall I install catalyst here?" and, on a yes, `catalyst init`.
- **Broken**: an agent that sees a project without catalyst and installs it to be helpful.

## L9. The kernel knows no module; no module knows another module or an agent

A module works alone, and beside any other. Modules and extensions act on the deployed project, never on catalyst
itself.

- **Kept**: the knowledge-base module reads a criterion through catalyst's CLI, whichever modules wrote it.
- **Broken**: a module whose command assumes the software-engineering module's requirement type exists.

## L10. Say what you did and what you checked

Outcomes are reported as they are: failed checks, skipped steps, claims not verified. It is called "catalyst".
Reports name repositories, never someone's local paths.

- **Kept**: "The tests pass; I did not run the integration suite, which needs Keycloak."
- **Broken**: "Done!" when one check failed.

## The software-engineering module's law

- **SE-L1. The tier decides the artifact.** A feature is a requirement (`REQ-`), whose steps (`STEP-`) are opened as
  the work happens, at least one before it closes. A fix is a bug (`BUG-`) against the rule it restores. A chore
  changes no rule's behaviour and has no artifact. A feature from the roadmap (`FEAT-`) becomes a requirement when
  work on it starts, never a bug.
